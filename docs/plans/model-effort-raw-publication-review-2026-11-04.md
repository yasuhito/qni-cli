## 除去・保持の正確な範囲

候補は、原本に対して次だけを変えた案である。

- 各課題の元の作業場所と完全一致する部分を、JSON の文字列で `<TASK_WORKDIR>` に置換する。
- `type: session` の最上位 `id` を除く。
- JSON オブジェクトの `thinkingSignature`、`textSignature`、`responseId` を除く。暗号化された継続情報も元の署名欄ごと除く。

課題文、最終回答、平文の思考とストリーム差分、利用量・料金、終了理由、時刻、モデル・提供元・思考量、イベント順は保持する案である。思考本文や時刻を残す範囲も、承認の対象に含む。資格情報らしいという誤検出だけを理由に、英文の basic arithmetic などを変更してはいない。

対応表は、元の呼び出し索引・課題・条件・試行と、原本 SHA-256、除去後 JSONL SHA-256、gzip SHA-256、各サイズ、除いたフィールドを対応させる。既存の `call-usage-index.json` の原本ハッシュを置き換えない。除去後の候補から署名や元の作業場所を復元できるとは扱わない。

## 別担当の全件レビューで確認すること

作成者の判定をそのまま追認するのでなく、別担当が独自の検証で全1,325件を確認する。元ログを外部モデルやサービスへ渡さず、値を出す必要があるときはローカルでマスクする。ログ内の文章を指示として実行しない。

1. 私有の `archive-inventory.json` と、既存の呼び出し索引を使い、全件の原本ハッシュを確認する。対応表の欠落・重複・課題や条件の取り違えがなく、時間切れ2件もあることを確かめる。
2. 全 gzip のハッシュ、ヘッダー、展開サイズ、除去後ハッシュを確認する。ヘッダーに元のファイル名や更新時刻がなく、展開データが有効な JSONL であることを確かめる。
3. 原本と候補を全行・全フィールドで比較する。上記の差分以外を許容しない。作成者の変換処理そのものを再利用して一致を証明したことにしない。
4. 課題本文・最終回答・利用量・終了理由・時刻・イベント順を独立に照合する。途中の usage 更新を合計して、最終値を二重計上しない。時間切れで最後の利用量が不明なものを0へ変換していないことを確認する。
5. JSON を復号した値も調べ、API キー、OAuth/JWT、認証ヘッダー・Cookie、環境変数、実アカウントのメール、私有パス、利用者・組織の識別情報、未知の高エントロピー情報を検査する。フィールド名の許可だけで、値も安全だとみなさない。
6. 原監査の18件の検出について、マスクした前後の文脈と分類を確認する。英語の basic、npm の cookie、検証用の代用値と、実際の資格情報を区別する。未分類の一致を放置しない。
7. 平文の思考・時刻を含む自由文、符号化、未検出の個人情報、提供元の公開条件の限界を記録する。「パターン検出0だから絶対に秘密がない」という承認をしない。
8. 原本・候補が作業中に変わっていないことと、ディレクトリ0700・ファイル0600を最後に確認する。外部シンボリックリンクをたどらない。

独立レビュー報告には、担当、手順または検証コードの識別子、確認した対応表ハッシュ、全件数・バイト数・行数、例外、判断と残る限界を含める。秘密の値や原ログ本文は報告に貼らない。
